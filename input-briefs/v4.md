# UrbanWear - Evolución V4

Marketing necesita poder evolucionar la configuración de cupones ya existentes
sin perder su identidad ni el historial generado por versiones anteriores.

Hasta ahora cada cupón posee una única configuración. A partir de esta versión,
un mismo cupón podrá tener diferentes configuraciones efectivas a lo largo del
tiempo.

Las reglas existentes de V1, V2 y V3 que no sean modificadas explícitamente por
este requerimiento deben continuar vigentes.

## Actualización de cupones

Agregar:

PATCH /coupons/:code

La actualización es parcial.

Los campos no incluidos en el PATCH deben conservar el comportamiento que les
corresponda según la configuración anterior del cupón.

El código identifica al mismo cupón durante toda su vida y no puede modificarse.

## Revisiones temporales

Cada PATCH genera una nueva revisión de la configuración del cupón.

Opcionalmente puede incluir:

{
"effectiveFrom": "2026-09-15T00:00:00.000Z"
}

Si `effectiveFrom` no se informa, el cambio entra en vigencia inmediatamente.

Si se informa una fecha futura, el cambio debe almacenarse pero no debe alterar
el comportamiento actual hasta alcanzar ese instante.

Un mismo cupón puede tener varias revisiones futuras programadas.

Las revisiones pueden ser creadas en un orden distinto del orden cronológico en
el que entrarán en vigencia.

Para cualquier checkout debe utilizarse la configuración que resulte efectiva
en ese instante.

## Herencia entre revisiones

Una revisión solo modifica los campos enviados.

Los campos omitidos deben heredarse de la configuración que corresponda
inmediatamente antes de esa revisión dentro de la línea temporal del cupón.

Esto también debe funcionar cuando existen varias revisiones futuras.

Por ejemplo, si:

- la configuración actual tiene descuento 20 % y mínimo 50;
- una revisión para el día 15 cambia únicamente el descuento a 30 %;
- posteriormente se programa una revisión para el día 20 que cambia únicamente
  el mínimo a 100;

a partir del día 20 deben quedar vigentes ambas modificaciones:
descuento 30 % y mínimo 100.

## Inserción de revisiones intermedias

Debe ser posible agregar posteriormente una revisión cuya fecha se encuentre
entre dos revisiones futuras ya existentes.

La línea temporal resultante debe continuar siendo coherente.

Los campos no modificados por cada revisión deben conservarse de acuerdo con la
secuencia temporal final, y no simplemente según el orden en que los PATCH
fueron creados.

## Activación

La configuración podrá incluir:

{
"active": true
}

Los cupones son activos por defecto.

Si la configuración efectiva posee `active: false`, el cupón no puede utilizarse.

Una revisión posterior puede volver a activarlo.

Desactivar o reactivar un cupón no debe reiniciar ningún historial.

## Límite configurable de usos

La configuración podrá incluir:

{
"maxUsesPerUser": 3
}

Si nunca se proporciona un valor, debe mantenerse el comportamiento existente.

El límite debe considerar todos los usos exitosos históricos del usuario para
ese mismo cupón, incluso aquellos realizados bajo configuraciones anteriores.

Modificar el límite no reinicia el contador.

## Historial e identidad

Todas las revisiones representan el mismo cupón lógico.

Los cambios de configuración no deben:

- crear un historial independiente;
- eliminar usos anteriores;
- reiniciar límites diarios;
- reiniciar límites totales.

Las restricciones de utilización deben evaluarse considerando toda la historia
del cupón.

## Combinación de reglas

Una revisión puede modificar cualquiera de las reglas configurables existentes,
incluyendo:

- tipo y valor del descuento;
- vigencia;
- monto mínimo;
- categorías;
- usuarios permitidos;
- estado activo;
- máximo de usos.

Las reglas que continúen vigentes deben seguir combinándose entre sí.

Una nueva revisión no implica que las demás validaciones dejen de aplicarse.

## Revisiones múltiples

Cuando existan varias revisiones aplicables, debe utilizarse la configuración
resultante de la secuencia temporal de revisiones hasta el instante del checkout.

Una revisión futura no puede afectar un checkout anterior a su `effectiveFrom`.

Al alcanzar exactamente `effectiveFrom`, la revisión ya debe considerarse
vigente.

## Compatibilidad

Los cupones existentes que nunca sean modificados mediante PATCH deben conservar
el mismo comportamiento que tenían antes de V4.

También deben continuar funcionando las APIs preexistentes y el checkout sin
cupón.

No se requiere una arquitectura interna específica para implementar las
revisiones.
